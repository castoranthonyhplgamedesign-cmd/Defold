1. RESOLVED 2026-10-16: iPhone performance during merge/clear chain reactions
=====================================================================
Cause: HTMLAudio SFX. Overlay showed sfx 393 ms/s over 18 plays (~22 ms per play()), worst frame 127 ms.
Fix: merge/pop play as Web Audio one-shots (audio.ts initWebSfx) once decoded; touch/gift/win stay HTMLAudio.
Device result (iPhone 15, AppLovin preview): no lag, every overlay field in the "good" range:
  fps 58-60, >20ms 0-2, worst <25, cpu <12, other <10, render <4, phys <3/1st, sfx <1/play, redraw <2.
History below kept for reference.

Symptom (iPhone 15, AppLovin Playable Preview): FPS drops when rings merge/clear,
worst during CHAIN REACTIONS (many balls transferring/popping every 80 ms).

Device measurements so far (dist-perf overlay):
  - Original canvas renderer ............ "fps drops" (no numbers)
  - Attempt 1: GPU DynamicTexture balls . WORSE: 15 fps, worst frame 334 ms  -> REVERTED
      (tile-based Apple GPU: ~15-20 render-target switches per ball redraw is costly)
  - Attempt 2 (current code):
      * ball canvases created with willReadFrequently:true (CPU-backed, no GPU->CPU readback before upload)
      * Ball.redraw() only queues; Ball.flushRedraws(1) renders max 1 ball per frame (Board.update)
      * shadow + dark base cached per ring count (RingArt.underlay)
    Device result: lowest 9 fps, worst frame 298 ms, redraw avg 0-2.00 ms, up to 28 redraws/s
    => BALL REDRAWS ARE NOT THE BOTTLENECK. Cause is elsewhere.

Suspects (not yet measured on device):
  a) Physics catch-up spiral: Matter positionIterations 20 / velocityIterations 10 (main.ts),
     fixed 60 Hz runner steps several times per frame after a slow frame.
  b) iOS <audio> SFX: merge/pop cue every 80 ms; HTMLAudio play()/currentTime in WKWebView
     can block the main thread (media process IPC). Desktop can't show this.
  c) WebGL upload / GC stalls outside game code ("other" time).
  d) WebGL render submission.

NEXT STEP: build dist-perf, play on iPhone, trigger a chain reaction, screenshot the overlay.
  PERF=1 npm run build        -> dist-perf/<variant>/... (same names, overlay on)
  npm run build               -> dist/ (shippable, overlay compiled out)
Overlay (src/utils/perf.ts), worst frame of each second:
  fps N  >20ms K
  worst Xms = cpu A + other B        (cpu = Phaser step start -> render end)
   render R  phys P/Sst              (physics ms / steps in that frame; >=3 steps = catch-up spiral)
   sfx S/N  redraw D/M               (sfx ms / plays; redraw ms / count)
  per s: phys ..ms  sfx ..ms/..
   redraw ../s  avg ..ms
Decision table:
  high phys + many steps -> lower Matter iterations, cap steps per frame
  high sfx               -> fewer pop/merge cues per chain, or move SFX to Web Audio
  cpu small, other huge  -> GPU/IPC/GC stall: textures at screen resolution, fewer allocations
  high render            -> fewer draw calls / particles
Untried idea: render ball textures at display resolution (sd scale) instead of design px (~36% fewer px on iPhone).

Perf hooks: Ball.render (perfFrame.redraw), audio.sfx (perfFrame.sfx), GameScene perfPhysics(matter.world),
main.ts startPerfHud(game). All gated by __PERF__ (vite define, PERF env) -> dead code in normal builds.

- Click variants (3clk/10clk): click = pointerdown on the player ball; last click ends immediately.
- Every end: auto-redirect to store, then endcard (toEndcard). EXCEPT fail: endcard only, no redirect.
  Board freezes under endcard (matter pause + scene.time.paused).
  WARNING: auto-redirect without a tap may violate Facebook/Google/MRAID network review rules.
- Win: WinFx.ts (gift flies to center, burst, sfx_gift) -> redirect -> endcard. sfx_gift no longer on ball clear.
- Fail: practically unreachable in normal play (same as reference). Danger.ts: rope pulses red while a ball
  rests above the line; red vignette last 0.5 s; then endcard. TryAgain.ts deleted.
- Analytics (AppLovin spec): LOADING, LOADED, DISPLAYED (after intro), CHALLENGE_STARTED,
  CHALLENGE_PASS_25/50/75 (gift sink progress), CHALLENGE_SOLVED, CHALLENGE_FAILED, ENDCARD_SHOWN, CTA_CLICKED.
  Auto-redirects are not counted as CTA_CLICKED. Caveat: AppLovin says skip analytics if the HTML
  redirects within 5 s of first interaction -> 3clk variant may qualify.
- Endcard logo sized by screen short side (same in portrait/landscape).
- Dev helpers (npm run dev): ?variant=3clk|10clk|60sec ; keys D (danger countdown), W (win), F (fail),
  L (limit end), or window.debug.*() in console. Stripped from builds.

  (Node 22+ has global WebSocket): launch chrome --headless=new --mute-audio --remote-debugging-port=9333,
